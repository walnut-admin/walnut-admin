## 四、逐块详细对比（8 块）

### 4.1 门禁编排与反向断言

- **Z 的模式**：`Z · packages/tooling/gates.json` 把「门禁名册」与「触发面 profile」分开，每个面显式声明自己的成员与 `external`（不在名册里但属于该面的检查）。断言群做的是**双向**：名册 → 真实接线，以及 CI 侧脚本 → 名册（否则必须写明 `runner-exempt: <原因>`）。
- **本仓**：`packages/tooling/scripts/src/ci/prepush.ts` 是一张扁平的表 + 并行 runner，**没有触发面维度**；`prepush.test.ts` 只做单向（`argv[0]` 能落到真实根脚本）。
- **差距的两个方向**：
  1. **漏失效**（A1）：CI 与发版电池对这张表没有任何约束；
  2. **误报风险**：Z 自己也踩过 —— 它的 `external` 字段一度变成「可以往里塞东西」的口袋，后来补了形状断言才收住。**照搬时必须同时补断言**。
- **负向验证**：Z 把「注入错误证明门禁会红」做成了**可重跑的工具**（带 HEAD 对账、写后读回、信号钩子还原），本仓是「一次性脚本手工注入 + 结果写进文档」——不可重跑。**它的安全壳值得学**（`finally` 不覆盖 SIGINT/SIGTERM，中途被杀会把注入**留盘**，下次运行反而把它当基线「还原」回去），但**要在下一次手工注入之前先落壳**。

### 4.2 CI 与发版编排

- Z 用 55 KB 的脚本来**校验自己的流水线定义**（断言「不该消失的阻塞门禁还在」、禁止形、引用的根脚本必须存在）。本仓唯一的 workflow 校验是 actionlint —— 它**只做语法**，语义层零覆盖。
- 回答一个关键可行性问题：**「secrets 不得出现在 `if` 里」这类断言在 GHA 上能不能做？能**，而且比 Jenkins 容易（我们是真 YAML，可按 job/step 结构判，不必做 Groovy 文本切片）。
- **本仓比 Z 强的两处**：发版电池的结构（见 D 表）；`--affected` 的空集自检。
- **本仓缺的**：CI 语义断言（= A1）；turbo 缓存跨 run（= C4）。

### 4.3 文档体系

- Z 的核心资产不是目录，是**一份 150 行的「文档宪法」**（分层 / 命名 / 头部 / 长度预算 / 生命周期 / 敏感信息 / 评审钩子）+ **一条机械门禁** + **一套显式状态词**（每篇标题后标「活 / as-of / 历史 / 提案」）。
- **本仓缺的三处**：
  1. **没有「文档规范」的单一权威**：今天散在 `apps/docs/AGENTS.md` 的十条约定、`apps/docs/src/zh-CN/content/adr/index.md` 的 ADR 形态、`check-doc-budgets.ts` 的表注释三处；
  2. **归档区没有「归宿」列、也没有收录判据**：`apps/docs/src/zh-CN/content/archive/index.md` 只有「类型 / 说明」两列，读者无法知道哪条结论还成立；
  3. **占位页**：`apps/docs/src/zh-CN/content/frontend/features/` 下 7 个 1 行的页（7–26 字节）。
- **Z 有一条我们没有的硬判据**：**「未闭环事项禁止进历史区」** —— 仍开着的待办必须先抽到台账或现行文档，才能归档。本仓的归档约定只写了「新增过程文档时在待办表里登记一行」，**没有这条禁令**。
- **⚠️ 实施陷阱**：把 `apps/docs/AGENTS.md` 的十条约定搬进新页之后，那个文件会掉到预算的一半以下 —— 而 `lint:doc-budget` 规定「**预算用不到一半也算失败**」，所以搬家必须**同时收紧预算数字**。

### 4.4 ESLint / tsconfig / vitest / AST

- Z 的 43.6 KB「本地规则」实为 **13 条**，每条都有 RuleTester 正反语料 + 两条「结构锁」（名册只增不减、模板分支必须注册）。本仓 `packages/tooling/eslint-config/nest-local-rules.ts` 只有 1 条规则，**全仓 0 个 RuleTester**。
- 13 条里**本仓适用且零误报**的只有两条（= C5）；其余要么被现有机制覆盖（精确版本靠 `saveExact` + syncpack）、要么无命中点、要么前提不同（中文棘轮）。
- tsconfig：我们把 Z 的 `ts + scripts` 两档合成了一档（`erasableSyntaxOnly` 在 `ts.json`），**属合理取舍**；可选补一条 `types: ['node']` 显式声明。
- vitest 预设：本仓 `include` **不含 `.tsx`**（当前全仓 0 个 `.test.tsx`，属**潜在**而非现存问题）；Z 还有「include 面偏离 src 时必须写明静默 0 用例风险」这条判据值得借。
- AST：本仓**已有一半**（`check-doc-ts.ts` 用 `ts.createSourceFile`、`check-turbo-cache.ts` 用 `parseConfigFileTextToJson`）；缺的是「脚本事实引擎」与「接线解析」——后者正是 B1 要用的。

### 4.5 产物门禁与安全闸

- Z 的挂载模式是「**声明式清单 + 三维接线**」：清单即数据（谁 × 画像 → 跑哪几条，含「是否读产物」以决定要不要透传画像），调度器按清单执行，入口挂在 app 构建链尾与根 `postbuild` 上。
- 它的**产物级去密断言**扫 dist 下全部文本产物，判密钥形态 / 内网网段字面量 / 设备口令字段 / `*.map` 存在性，规则表与它 CI 侧的密钥扫描**读同一份**（按 id 取用，改名不同步会当场抛错）；豁免按 **sha256** 记账，**不回显原文**。
- **本仓产物侧门禁为 0**。已有构建期能力（混淆 / CSP / 压缩 / Sentry / CDN）**一个都没有产物侧消费者**。
- **B5 落地时对上了它的第 4 / 5 / 9 条教训**（这也是这轮唯一"照着教训写"的地方）：
  - 第 4 条（每段都要能回答"这次实际扫了多少"）→ 输出固定打印 `1471 个文件 / 12.68 MB；扫文本 490，跳过压缩/二进制 981` 与 `拿 49 个机密值比对过`。实测全程 **424 ms**。
  - 第 5 条（不回显原文）→ finding **只报键名与文件、永不回显值**，用例里有一条专门钉它（连 `JSON.stringify(finding)` 都要干净）。
  - 第 9 条（判据要能被负对照证伪）→ 两条负对照都真跑过：① 把 api.conf 的安全头删掉 → `lint:nginx-headers` 当场红；② 把**真 env 值**注入一份产物副本（副本在系统临时目录、跑完即删）→ `lint:dist` 退出码 1 且不回显。
  - 另外它第 2 条的教训在这里**反向用了一次**：正因为"子串匹配容易被满足"，本仓的规则表**只收在真产物上零误报的规则** —— 被删掉的 3 条候选规则（裸 PEM 头 / 键名=值 / 超长 base64）各自有 1 / 8 / 5 次实测误报。
- **⚠️ 2026-09-23 补记：产物侧做完当天就漏了一次，而漏在"源码侧根本没人看"**。
  我在一个测试夹具里写了腾讯云文档的样本 SecretId（`AKID` + 32 位），**14 段 prepush 门禁 + 300 多个用例全绿**，
  然后 `git push` 被 **GitHub 服务端的 push protection** 拒掉。三条教训已落成新门禁 `pnpm lint:secrets`：
  ① **服务端那道闸在 CI 之前** ⇒ 必须在 `prepush` 拦；② 它**只认形状、分不出样本与真货** ⇒
  本仓规矩是「**假样本也不许长成真凭据的形状**」（夹具运行时拼装，**不加白名单** —— 服务端不读我们的白名单）；
  ③ 规则表与产物侧**同源**（共用 `scanText`），源码侧另立一套必然漂移。
  这也把本节那句「规则表与 Z 的 CI 密钥扫描同源」从**意图**变成了**事实**。
- **从它的安全评审里提炼的门禁设计教训**（这些比它的规则本身更有价值）：
  1. **单向断言 = 没有断言**（删掉调用点全链路仍绿）；
  2. **子串匹配的断言可以被一行注释满足** —— 断言必须**剥注释后**匹配命令位置；
  3. **被检对象与执行对象必须是同一份文件**；
  4. **每条规则都要能被问「这次实际扫了多少文件」**，答不出就是恒关；
  5. **白名单里永远不许出现明文凭据**（它曾把整枚 Key 抄进放行名单）；
  6. **豁免必须带机器可读字段**（到期条件 / 证据路径），自由文本理由无人核验；
  7. **新门禁忘进名册 = 静默死代码** —— 所以「进名册」或「写明为何不进」应当**二选一强制**；
  8. **恒红的门禁与没有门禁等价**（与本仓「宁可漏报不可误报」同源）；
  9. **一条判据要能被负对照证伪**（改坏它必须变红），否则只是安慰剂。

### 4.6 包标准与依赖治理

- Z 有 **22 条机械规则**，分 6 类（结构 / exports / scripts / 依赖 / tags 边界 / 文档）；规则数据住 JSON、判定住脚本。本仓 **0 条**，对应物是散文。
- **最能落地的一条是 `turbo-tags`**（= C2 的首项）。
- Z 的 `check-lockfile` 守 5 条不变量，其中 **L5（catalog 解析版本 == 声明值）是本仓最该补的**（= B2）。
- **本仓的 catalog 护栏其实比 Z 多**（`hoist: false` / `minimumReleaseAge` / `trustPolicy` / `blockExoticSubdeps` 它都没有）；它唯一比我们强的是 L5。
- **B2 落地时踩到的坑（值得单记）**：Z 的 L5 是「比工作区的 catalog 与锁文件」，照搬过来**永远绿**。原因是实测发现
  **pnpm 12 默认会在跑任何脚本之前自动 install**（`verifyDepsBeforeRun` 未设置时的默认行为）——
  `pnpm lint:lockfile` 会先把锁文件改对，门禁看到的已是同步状态。判据：注入一个「存在但不同」的 catalog
  版本，`pnpm <script>` 路径 exit 0（且锁文件被 pnpm 改了），而 `node <bin>` 直跑 exit 1 并报出是哪一条。
  **改法**：比对对象从工作区换成 **`git show HEAD:` 那两个文件** —— CI 检出的正是这一对，与 pnpm 的
  自动 install 无关。这也是本项目里「一个门禁要能被问『它这次到底看了什么』」的又一个实例。
- 一条可以直接用的判据：**「枚举类事实一律不复述」** —— Z 把包清单 / 脚本清单 / 门禁清单全部指向那几份 JSON，正文只写判据。本仓已有半条纪律（「别写会腐烂的计数」），缺的是「指向唯一真源」的落点。
- 顺带查到本仓三处**零消费者的元数据**：`walnut` 自定义字段（14 个包在写，全仓无读取方）、`contract` 与 `utils-core` 同时有 `main` 与 `exports`、9 个包无 `private`。Z 的等价信息是从 `exports`/包名**推导**的，理由是「手写分类必然与事实漂移」。

### 4.7 git 钩子 / 提交纪律 / 开发体验

- `lefthook.yml` 两边几乎逐字相同；**差异在断言圈**：Z 主动**禁掉** `skip` / `only` / `glob` / `exclude_tags` 这些「让 job 永不出场」的键，本仓没有这层检查。
- **命令行公共层是唯一量化得出来的结构差距**（= C1）。
- 子进程层**我们不缺能力**（心跳 / 预算 / 平台分支 / 输出尾缓冲 / 进程树回收都有），只差 POSIX 的 SIGTERM→SIGKILL 升级。
- 根脚本：逐组核过，**没有重复转发或同 target 双名**；缺口是「没有机制拦住未来的漂移」（= C3）。
- **A2 就在这里**：`hooks:check` 是「本机钩子还活着吗」的检查，而 prepush 本身就是钩子调的（**循环**），所以它只能在**不经钩子的入口**（`pnpm release`）里生效 —— `lefthook.yml` 那句注释描述的正是这个意图，只是没实现。

### 4.8 提案 / 调研文档、部署、类型

- Z 的**提案区**有三态生命周期（提案 → 落地即删 / 放弃即删，**不保留已否决档案**），调研区定位为 **as-of 快照**（不随代码维护、冲突以代码为准）+ 文件名日期前缀**仅该目录允许**。
- **与本仓的直接冲突**：本仓**刻意保留执行记录**（`architecture-todo.md` 的执行记录 / 核实记录），Z 是「落地即删」。**两者选一，不要混**。
- Z 的调研文档有两个可直接借的**写法**：头部「定位 / 读者 / 权威边界」三行，与末尾专设「**未核实 / 不可引用**」节（本页第二节就是这套写法的应用）。
- 部署：`nginx.conf` 与我们的差（见 D 表）。原先这里写着「值得补的有两档」，2026-09-23 把两档都核了一遍，结论是**只剩一档**：
  - ❌ **「运行时配置类资源禁缓存」在本仓不适用**（不是"没做"）：本仓是**构建期注入** env 的纯 SPA，产物里没有任何运行时配置文件 —— 实测 `apps/admin/dist` 顶层只有 `assets/` `static/` `vendor/` + 两个 favicon + `index.html`，**没有 `.json`**。没有那个东西，就没有那条规则要防的失败。
  - ✅ **安全响应头**（B4）：不是"学它"，而是这块**两边都不合格** —— 本仓动手时实测出自家的 `api.conf` 一个头都没有。
- **顺手把缓存策略也实测了一遍**（因为上面那条要判"适不适用"，必须先知道我们到底缓存了什么）：
  - `location /static/` 的 `expires 1y; immutable` **是对的** —— 实测该目录下 **484 个非压缩文件全部带 hash**（换内容必然换文件名，所以"换不掉"这个经典事故不成立）；`index.html` 没有任何缓存头（SPA 最怕的那条坑不存在）。
  - `assets/` 与 `vendor/` 是**稳定文件名**（`assets/ai_finish.mp3`、`assets/css/driver-dark.css`、`vendor/codeMirror/langs/zh-CN.js`）且**没有任何缓存头** ⇒ 每次重新验证。**结论：保持不动** —— 给稳定名加长缓存才是危险方向（改了用户拿不到），真要收益应当先让那些文件 hash 化，那属于构建配置，不在这一档里。理由已就地写进 `deploy/nginx/frontend-server.conf` 的注释。
- 类型 / schema：Z 用 `ts-json-schema-generator` 生成**交付契约**；本仓的 `genJSONSchemas.ts` 生成的是编辑器提示用的 schema（无消费者、无门禁）。**不建议现在扩成契约** —— 本仓没有「客户配置文件」这类交付物。

|---|------|------|-----------|
| Q1 | `hooks:check` 怎么收口 | ✅ **真加进发版电池** | 这个检查只能在**不经钩子**的入口生效（prepush 本身就是钩子调的，是个循环），`pnpm release` 正是那个入口。`lefthook.yml` 那句注释描述的意图是对的，补上实现即可 |
